AZ01 v1 update-image container -- reference notes
=================================================
Source file: Force-3.10.0-update.img (186528232 bytes), Akai's official Force 3.10.0 update.
Cross-checked against MPC-3.10.0-Gen1-update.img (167084848 bytes).
Only the container metadata is reproduced here; no payload is included beyond the first bytes shown in the dump.

All integers are LITTLE-ENDIAN. "str" and "blob" are length-prefixed:
  str  = u32 len (bytes, excluding NUL) + len bytes + NUL + zero padding so the whole
         string field (bytes+NUL+pad) is align4(len+1) bytes.
         e.g. "rootfs"(6) -> 4 + 8 bytes; "sha1"(4) -> 4 + 8 bytes; "inmusic,ada2"(12) -> 4 + 16 bytes.
  blob = u32 len + len bytes + zero padding to align4(len)   (no NUL)

Records (from align8(header_len) until the EOF record)
------------------------------------------------------
Every record starts with the same 16-byte prefix:
  +0x00  4  char[4]  tag: "PART" or "EOF\0"
  +0x04  4  u32      record header length in bytes, counted from the tag up to the first payload byte
  +0x08  8  u64      payload length in bytes (the payload follows the record header directly)

PART record (Force: at 0x78, header length 0x4c = 76):
  +0x00  4    "PART"
  +0x04  4    u32  0x4c                     record header length
  +0x08  8    u64  186528020 (0x0b1e3114)   payload length (compressed size)
  +0x10  var  str  "rootfs"                 target partition, by GPT PARTLABEL
  +0x1c  var  str  "xz"                     payload compression ("xz" = standard .xz stream)
  +0x24  4    u32  1                        number of hash entries that follow
  +0x28  var  str  "sha1"                   hash algorithm (strings in libaz01-prog also know "sha256")
  +0x34  var  blob 20 bytes                 hash value: 693ff81c8fd36eb1f9de5ed285703436fe41c2bc
  +0x4c       payload: 186528020 bytes of xz data (begins fd 37 7a 58 5a 00), decompresses to
              a raw ext4 image of 473595904 bytes, which is written to the "rootfs" partition (500 MiB).
  The next record starts at align8(payload end). (Both observed images end their payload on an
  8-byte boundary already, so the presence of padding there is inferred from the header case.)

EOF record (Force: at 0x0b1e31d8, last 16 bytes of the file):
  +0x00  4  "EOF\0"
  +0x04  4  u32 0x10   record header length (16)
  +0x08  8  u64 0      payload length 0
  The EOF record ends exactly at end of file (Force: 0x0b1e31e8 = file size).

What the sha1 covers
--------------------
The SHA-1 in a PART record is computed over the PAYLOAD BYTES AS STORED IN THE FILE (the compressed
.xz stream, exactly payload_len bytes). It does NOT cover the decompressed data, the record header, or
the file header. Verified for both images (compressed: match; decompressed: no match).
There is no signature anywhere in a v1 container; integrity is the per-partition hash only.

Multiple PART records
---------------------
The record framing (tag + header length + u64 payload length, terminated by an explicit EOF record)
allows any number of PART records in sequence, one per target partition. Both official 3.10 images
contain exactly one (rootfs), so multi-PART files are not confirmed against a real Akai image.

Verification
------------
A throwaway Python parser walked both images with exactly the rules above, asserted that every header
and record parsed to its declared length, that the EOF record ends at end of file, and recomputed the
SHA-1 over the payloads:
  Force-3.10.0-update.img        rootfs xz 186528020 bytes  sha1 693ff81c...c2bc  OK  -> 473595904 bytes ext4
  MPC-3.10.0-Gen1-update.img     rootfs xz 167084492 bytes  sha1 668af0cc...1121  OK  -> 451468288 bytes ext4

Updater strings (text summary, from libaz01-prog.so.1.3 and the update ramdisk's /usr/sbin/init)
-------------------------------------------------------------------------------------------------
Magics recognised: "AZ01" (this binary v1 format) and "AZ0x" (newer formats). libaz01-prog exports
az01_image_v2_ops, az01_image_v3_ops and az01_image_fdt_ops: v2/v3 are FDT (device-tree blob) based
images with signatures (az01_image_for_each_signature, az01_verify_signature, RSA "sha256,rsa2048",
public keys looked up in /usr/lib/az01/pubkeys and /usr/lib/az0x/pubkeys as <name>.pub).
FDT image keys/nodes seen: /images, /configurations, default, description, compatible,
  inmusic,devices, inmusic,version, inmusic,generation-number, partition, compression, data,
  data-offset, data-size, data-position, hash, algo, value (algos: sha1, sha256).
Partition / target names seen: rootfs (from the v1 PART record), data (erase-data-partition),
  spl, u-boot, uboot-spl, uboot, spl1, spl2, uboot1, uboot2 (bootloader writes), config;
  GPT on the Force also has env, splash, recoverysplash, synths.
Compression: xz (liblzma, multi-threaded stream decoder; index used to learn the uncompressed size).
Update flow strings: the running system stores the image (default path /data/az01-update.img), then
  either reboots with "--reboot-argument=update:<dev>:<file>" or kexecs /boot/zImage with
  /opt/ramfs-update.squashfs as ramdisk and "ramdisk_size=32768 root=/dev/ram0 ro -- upgrade-device=%s
  upgrade-file=%s". The ramdisk init mounts the source device (exfat/ntfs-3g/etc.), verifies the image
  ("verifying image (%s)...", "image verified OK"), then "writing partition %s (%zu bytes)".
  Other ramdisk options: upgrade-debug-shell, upgrade-fallback-shell, erase-data-partition.
  Updates and data erase are refused unless on mains power
  (/sys/class/power_supply/az01-ac-power/online or .../mains-power/online).
  Compatibility is checked against /sys/firmware/devicetree/base/compatible, inmusic,product-code
  and inmusic,az0N-pcb-rev.
USB (fastboot/rockusb) commands seen: getvar:max-download-size, getvar:power-source, getvar:partition-type:%s,
  getvar:version-bootloader, getvar:sparse-image-support, download:%08x, flash:%s, erase:%s,
  reboot-bootloader, oem fetch-pubkey:%s, oem flash-bootloader, oem update-bootloader, oem format,
  oem resetenv, oem set-panel-map:%s, oem set-flag:%s, program-fuses.
